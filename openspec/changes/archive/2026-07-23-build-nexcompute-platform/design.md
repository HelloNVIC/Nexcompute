## Context

Nexcompute 是一套面向高校/实验室场景的分布式 GPU 算力管理平台。物理形态：多台 Windows + GPU 主机散布在实验室局域网内（可能在 NAT 后），一台管理服务器统一纳管。使用形态：导师按课题组把机器分给学生，学生在分配到的机器上创建 Docker 容器跑训练，通过 SSH 或 Web 应用端口访问容器。

技术栈已由需求锁定：管理端 SpringBoot + Vue/AntD/ApexCharts + PostgreSQL + Redis；受控端 Go + GUI；容器 Linux only via Docker Desktop WSL2；一机一 GPU。

利益相关方：管理员（运维全部资源）、导师（管理本课题组学生与资源）、学生（使用分配到的机器）。

## Goals / Non-Goals

**Goals:**
- 管理端单一实例统一纳管所有受控物理机
- 受控端全出站连接（心跳 + WS），穿透 NAT/防火墙
- 容器创建全链路：表单 → 生成命令 → 受控端执行 → 连接信息回传
- 存储池按项目隔离，支持共享与跨机迁移
- 镜像 tar 化管理，公共库自动同步，私有镜像按归属与可见性控制
- 三角色 × 模块 × 操作的权限矩阵，全操作审计
- 直连模式下用户通过 物理机IP:端口 访问容器

**Non-Goals:**
- 穿透模式（预留 UI，本期「敬请期待」）
- 管理端高可用 / 集群部署
- GPU 多卡、MIG 分片、显存硬隔离（一机一卡，软共享）
- 镜像 Registry 服务（用 tar 文件方案替代）
- 镜像层去重、版本回滚
- 受控端之间的直接通信（所有中转走管理端）

## Decisions

### D1: 通信架构 -- 心跳保活 + 独立 WS 命令通道（方案 C）

**选择**：受控端定时发 HTTP 心跳上报状态（CPU/GPU/温度/内存/进程）；另建一条独立 WebSocket 长连接用于命令派发与结果回传。两条通道都是受控端主动发起的出站连接。

**理由**：实验室机器通常在 NAT/防火墙后，全出站最稳。纯心跳轮询的命令延迟体验差（PowerShell 结果要等下一轮），纯 WS 又不便做低频状态采样。拆成两条各司其职：心跳走 HTTP 简单可靠，WS 只跑命令与实时结果。

**备选**：
- 纯心跳 + 响应携带命令：延迟高，PowerShell 交互体验差
- 纯 WebSocket：状态采样挤占命令通道，连接管理复杂
- gRPC 双向流：能力足够但 Windows 上 Go gRPC 栈偏重，且 WS 对 Web 前端更友好

### D2: Docker API 本地化 -- 受控端作为唯一 Docker 代理

**选择**：Docker daemon 不开放远程 API。所有 Docker 操作由管理端通过 WS 下发命令，受控端在本地调用 Docker API 执行。

**理由**：Docker 远程 API 暴露 = 容器逃逸 = 宿主 root，是最高危攻击面。受控端作为代理层，既隔离了 Docker API，又便于审计（所有 Docker 操作都经过管理端命令链路，可记录）。

### D3: 镜像管理 -- tar 文件方案（非 Registry）

**选择**：`docker save` 导出 tar，以文件形式存于管理端文件系统；使用时传到目标受控端 `docker load`。镜像元数据（归属、可见性、大小、标签）存 PostgreSQL。

**理由**：
- 不需要运行额外的 Registry 服务，部署简单
- 权限模型（学生->导师可见、管理员全可见）在管理端 DB 里管，与用户体系天然打通，比 Harbor 的项目权限模型更贴合三角色体系
- tar 是文件，好备份、好离线迁移

**代价（已知接受）**：无层去重（多个同 base 镜像各存一份）、无版本历史（靠命名区分）、传输整包无增量。

### D4: 存储池模型 -- 项目级，一用户一机器多池

**选择**：存储池命名 `物理机编号-工号/学号-项目名`（如 `01-2021001A-bert-finetune`）。一个用户在一台机器上可创建多个项目存储池。同一项目名在不同机器上是两个独立池。迁移按单个项目池进行。

**理由**：比「一用户一机器一池」更灵活，项目间数据隔离干净，共享与迁移粒度更细。

### D5: 存储池迁移 -- 管理端中转 + 断点续传

**选择**：迁移数据流 `受控端A → 管理端(中转) → 受控端B`，复用 `file-transfer` 能力。前置条件：无运行容器使用此池。失败断点续传，原池保留直到成功，迁移成功后用户确认才删源池。只迁用户数据，不迁容器。

**理由**：受控端之间不直连（Non-Goal），中转虽慢但架构简单。断点续传应对大文件与网络抖动。用户确认删除防止误操作。

### D6: 连接模式 -- 仅直连，穿透预留

**选择**：受控端初始化时选「直连」或「穿透」。本期只实现直连：用户通过 `物理机IP:宿主端口` 访问容器 SSH 与应用端口。穿透模式 UI 显示「敬请期待」。

**理由**：穿透模式需要在管理端内置反向隧道子系统（类 frp），是独立的复杂子系统。先砍掉以加速 v1 交付，直连模式在局域网实验室场景已可用。架构上为穿透预留连接模式字段。

### D7: SSH 访问 -- 容器级密码，创建时设置可即时重置

**选择**：SSH 密码在容器级别管理。创建容器时用户 MUST 设置该容器的 SSH 密码。用户可对单个容器重置 SSH 密码，重置即时生效（受控端通过 `docker exec` 更新运行中容器密码）。公共镜像库镜像必须预装 sshd。

**理由**：容器级密码比用户级更灵活，每个容器独立密码降低单点泄露影响。即时重置提升安全性与便利性。

**备选**：用户级统一密码（一个泄露影响所有容器）、密钥对（用户要管私钥，更重）。

### D8: 端口分配 -- 系统自动分配

**选择**：用户在容器创建表单中声明容器内端口（SSH:22 + 自定义如 8888），系统在目标物理机上自动分配宿主端口并映射，防止单机端口冲突。分配表存管理端，连接信息回传给用户。

**理由**：用户无需关心宿主端口选择，系统保证无冲突。管理端需要知道端口才能生成连接信息，所以由管理端分配而非受控端。

### D9: 资源分配 -- 机器级，可共享

**选择**：导师分配「机器」给学生。一台机器可分给多个学生。学生在分配到的机器上自由创建多个容器。容器创建时设 GPU 显存 / CPU / 内存限制（同课题组自协调争抢）。导师配额仅限机器维度。

**理由**：颗粒度简单，符合实验室「这台机器分给你用」的直觉。资源限制由 Docker `--gpus`、`--cpus`、`--memory`、`--shm-size` 等实现。GPU 软共享（多容器见同一卡）接受，不做硬隔离。

### D10: 公共镜像库 -- 管理端维护，受控端自动同步

**选择**：管理员在管理端上传/管理公共基础镜像 tar。受控端启动时 + 每隔固定时间，向管理端拉取公共镜像列表，有新增则下载 tar 并 `docker load`。

**理由**：用户无法直接 pull 镜像（Docker API 不开放）。公共库自动同步保证所有机器上有相同的基础镜像供用户选择。复用 `file-transfer` 的下载能力。

### D11: 权限矩阵 -- 角色 × 模块 × 操作

**选择**：三个固定角色（管理员/导师/学生）。管理员可在「用户权限矩阵配置」中对每个角色 × 每个模块勾选「查看/编辑/删除」细粒度权限。前端按矩阵渲染菜单与按钮，后端按矩阵鉴权。

**理由**：比纯硬编码角色权限灵活（管理员可微调），比完全自定义角色简单（角色固定三个）。

### D12: 审计 -- 全操作入库

**选择**：所有用户操作（容器管理、存储池操作、镜像操作、PowerShell 执行、权限变更等）写入 PostgreSQL 审计表，记录操作人、时间、目标、内容、结果。PowerShell 远程执行额外强调（仅管理员、仅物理实例管理入口）。

### D13: GPU 显存软限制

**选择**：容器创建表单的 GPU 显存字段为**软限制**（注入环境变量提示框架自觉，如 `PYTORCH_CUDA_ALLOC_CONF`、TF memory fraction），非 cgroup 级硬隔离。CPU 与内存为硬限制（Docker `--cpus`、`--memory`）。

**理由**：NVIDIA 消费卡/Quadro 不支持无 MIG 的显存隔离，一机一卡不做 MIG（Non-Goal）。硬限制不可行，软限制 + 同组用户自协调是唯一可行方案。表单保留字段以提供指导值。

### D14: 工单类型、可见性与简化流转

**选择**：工单类型固定五种：资源申请、故障报告、特殊配置、权限申请、镜像申请。可见性：学生看自己的，导师看自己 + 课题组学生的，管理员看全部。所有工单直接派给管理员，管理员回复并关闭。状态流转简化为：待处理 -> 已关闭。工单变动通过未读消息通知提交学生。

### D15: 注册链接机制

**选择**：注册链接使用 UUID。导师创建时设置可用次数与过期时间（两者皆可触发失效）。导师可主动作废链接。任何持有链接者均可注册。注册必填：姓名、工号/学号、密码、邮箱、手机号。注册成功自动加入导师课题组，角色为学生。

**理由**：UUID 不可猜测；次数 + 时间双失效防滥用与长期泄漏；导师作废应对链接外泄。注册信息完整便于管理。

### D16: 受控端 GUI 形态与本地管理员密码

**选择**：受控端以系统托盘常驻运行，开机自启动，启动即获取整体管理员权限。关窗口缩到托盘不退出。退出受控端需输入「本地管理员密码」。该密码由管理端下发并保存于受控端本地。

**理由**：实验室机器上学生使用，需防止学生关闭/卸载受控端以逃避监控。托盘常驻 + 退出密码保护确保受控端持续运行。管理员权限用于 Docker 操作、系统重启、息屏、PowerShell 等命令执行。

### D17: 容器可见性 -- 仅数量

**选择**：同物理机上其他用户的容器对当前用户不可见（容器列表仅展示自己的）。物理实例状态页展示聚合数量（「另有 N 用户 M 容器」）。导师看课题组学生的容器，管理员看全部。

**理由**：保护用户隐私，避免相互干扰。数量统计满足「了解机器负载」的需求。

### D18: 进程查看范围

**选择**：管理员可查看 Windows 宿主机全量进程（运维排障）。学生仅可查看自己 Docker 容器内的进程。导师可查看自己课题组学生 Docker 容器内的进程。

**理由**：宿主机进程暴露其他用户活动，仅管理员可见。容器内进程属于用户自己的工作空间，可查看。

### D19: 监控数据 -- SSE + 历史存储 + 可配置粒度

**选择**：监控状态数据由后端保存至数据库（历史数据持久化）。前端通过 SSE（Server-Sent Events）接收实时推送。数据采集粒度可配置，默认 5 秒。

**理由**：SSE 单向推送足够图表场景，比 WebSocket 简单。历史存储支持趋势回溯。可配置粒度适应不同规模与存储容量需求。

### D20: 存储池根目录不可改 + 本地管理员密码保护

**选择**：存储池根目录设置后不可修改。如需修改，需输入「本地管理员密码」（与 D16 退出受控端密码相同，由管理端下发）。

**理由**：根目录变更会导致已有池路径失效、Docker 挂载引用断裂。设为不可改防止误操作。允许管理员通过密码修改以应对磁盘扩容等运维需求。

### D21: 监控历史数据保留 30 日

**选择**：监控历史数据保留近 30 日，超过 30 日的数据自动清理（定时调度任务）。

**理由**：平衡趋势回溯需求与存储成本。30 日足够排查近期问题，超期数据价值递减。

### D22: 存储池共享撤销 -- 提示与联系方式

**选择**：撤销共享时若有运行中容器正在使用该存储池，系统 SHALL 提示所有者具体卡在哪些容器，并提供相关用户（被共享方）的联系方式，以便协调停止容器后再撤销。

**理由**：避免强制停止影响他人工作，提供联系方式让用户自行协调，符合实验室协作场景。

### D23: 公告与未读消息系统

**选择**：管理员通过「公告管理」模块发布系统公告，支持定向发布（全体 / 指定课题组 / 指定角色）与定时发布（设定发布时间，到点自动发布）。所有用户拥有未读消息收件箱，接收三类通知：自己容器/存储池的变动、工单变动、新公告。消息有已读/未读状态跟踪，已读消息永久保留供回溯查询。通知由各业务模块事件触发，通知系统作为横切关注点统一管理。

**理由**：定向 + 定时满足差异化触达需求（如只给某课题组发、或定时发布维护通知）。永久保留已读消息便于用户回溯历史变动。公告是单向广播通道，未读消息是用户专属事件收件箱，两者结合覆盖信息触达。

### D24: 前端推送 -- SSE（复用监控与通知）

**选择**：管理端向前端浏览器的实时推送统一使用 SSE（Server-Sent Events）。监控数据（D19）与通知消息（D23）复用同一套 SSE 基础设施，通过 SSE 事件类型（`event` 字段）区分通道（如 `monitoring` / `notification`）。受控端 ↔ 管理端仍用 WebSocket（D1，需双向命令/结果）。

**理由**：
- 前端只需服务器单向推送（监控数据、通知），SSE 足够且比 WS 简单（浏览器内置 EventSource API、自动重连、标准 HTTP 穿透防火墙）
- WS 保留给真正需要双向的受控端通信
- 复用一套 SSE 连接推多类事件，减少前端连接数，SSE 原生支持事件类型分通道

**SSE vs WebSocket 关键区别**：SSE 单向（服务器->客户端）、基于标准 HTTP、仅文本、浏览器自动重连；WebSocket 双向全双工、独立协议、支持二进制、需手动重连。单向推送场景选 SSE，双向交互场景选 WebSocket。

## Risks / Trade-offs

- **[直连模式暴露物理机 IP]** → 用户需能访问物理机网络；实验室局域网内可接受，跨网段需 VPN。穿透模式后期补齐。
- **[SSH 固定密码安全性弱]** → 密码由用户自设，建议复杂度校验；容器隔离限制了爆破影响面。可后续加密钥选项。
- **[tar 无层去重，磁盘膨胀]** → 管理端需提供「清理未使用 tar」运维功能；实验室规模可控。
- **[管理端单点]** → 管理端宕机则无法管理容器（但直连模式下已运行容器仍可访问）。Non-Goal 接受。
- **[迁移走管理端中转，大池耗时长]** → 断点续传缓解；用户确认删除防误删。超大数据迁移可后续优化为受控端直传。
- **[GPU 软共享导致 OOM]** -> 显存为软限制（D13），同机用户需自协调。文档提示。
- **[WS 断连时命令丢失]** -> 命令需有幂等/重试机制；受控端重连后同步状态。心跳独立于 WS，断 WS 仍能保活上报。
- **[公共镜像同步占用受控端磁盘]** -> 同步策略可配置（全量/按需）；管理员可控制公共库规模。
- **[受控端以管理员权限运行]** -> 权限较大，受控端代码需严格校验命令来源（仅执行经鉴权的管理端命令）。本地管理员密码防止学生退出。
- **[注册链接泄露]** -> 次数 + 时间双失效 + 导师可作废；任何持有者可注册为设计意图（链接即邀请）。
- **[监控历史数据膨胀]** -> 可配置粒度（默认 5 秒）+ 需设计数据保留/归档策略（定期清理旧数据）。
